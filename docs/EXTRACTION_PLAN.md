# Approved extraction plan

Status: architect-approved scope; implementation and acceptance remain unverified until the destination tests and hosted checks are recorded.

## Objective

Retain every reusable source capability as a real, reachable, independently optional implementation in a generic single-business web platform. Preserve the existing Vinext/React application surfaces, domain services, relational data model, and behavioral lifecycles. This is an extraction of hosting and identity boundaries, not a rewrite permission or a reason to delete modules, collapse services into generic CRUD, or replace operations with metadata-only placeholders. A retained capability must have a reachable interface, a real enabled operation, isolated configuration, authorization as applicable, and an enabled-path test.

The target preserves the application framework and domain code while replacing every ChatGPT Sites build, publish, identity/proxy, and scheduled-task mechanism with ordinary Cloudflare Workers/Vinext tooling and standalone application boundaries. It uses one dedicated D1 database per installation, with additive checked-in Drizzle migrations preserving existing relational records and lifecycles. It does not depend on the source application's Sites runtime or native authentication/scheduling machinery. Cloudflare account OAuth and optional developer skills are not bundled runtime dependencies.

## Security and deployment boundary

- **Installation scope:** one business and one stable `INSTALLATION_ID` per Worker/D1 deployment. No cross-installation data access.
- **Business defaults:** do not ship fixed identity, contact details, service areas, timezone, seasonal dates, logo, or vertical-specific help claims from the original demo. The owner configures these for the installation; date validation uses its explicit configured timezone. Reusable domain behavior remains, while business facts and service vocabularies come from tenant configuration.
- **Owner provisioning:** an installer explicitly allowlists the owner identity before admin use. There is no first anonymous claim or client-selected owner. Missing/invalid owner configuration fails closed.
- **Login and sessions:** Google identity is verified server-side. A successful login creates a secure HttpOnly session. State-changing owner requests enforce same-origin/CSRF protection. Customer identities and admin-owner identities are distinct principals.
- **Storage:** preserve the original relational schema and domain-store lifecycles in D1. D1 is authoritative. Schema changes are checked-in versioned Drizzle migrations applied by deployment/install tooling, never by HTTP requests. Migrations are additive and preserve existing rows. Configuration writes use revision compare-and-swap; business actions and configuration changes are audited with secrets/PII redacted.
- **Feature state:** each optional module is `disabled`, `unconfigured`, or `ready`. Absence of an optional binding/provider never prevents core startup. “Ready” requires valid configuration and explicit enablement; key presence alone is not enablement.
- **AI:** one global AI gate defaults off and every AI-backed capability has a separate server-side gate. Both are rechecked immediately before model dispatch and queued/background execution. If either is off, there are zero AI calls. Workers AI is the first provider. No paid AI account is required for installation or core operation.
- **External calls:** no provider call, booking, OTP, notification, webhook delivery, payment, or paid inference occurs in tests. Production features use bounded requests, safe redirects, strict schemas, timeouts, idempotency/revision checks, and safe error translation.
- **Content:** manual details and explicitly pasted source text create source-backed drafts. A supplied HTTPS URL is provenance metadata only in the current onboarding flow; the app does not fetch it. Reject private/non-HTTPS URL values and never make an outbound request from this flow. If network retrieval is implemented in a later approved change, it must add bounded DNS/IP/redirect/body/time SSRF defenses and revalidate every redirect destination. Only an explicitly authorized owner can approve publishing, against the current draft/config revision. No model or import can authorize its own publication.
- **Secrets:** platform bootstrap secrets (including the credential-encryption key) live in the hosting platform's secret store. Provider credentials explicitly saved by the owner are encrypted with that key and installation-bound in the D1 credential store; they are never retained as plaintext configuration. Never expose secrets in source, documentation, chat, command arguments, logs, ordinary API outputs, or test fixtures.
- **Deployment:** preserve the established Vinext app, Workers/D1 bindings, and application routing while using current official Cloudflare/Vinext build and deploy tooling. The README's official Deploy button is for a public GitHub/GitLab repository and creates resources in the installer's Cloudflare account. Manual setup remains available. A pinned bootstrap helper and official framework/skills references must be supplied in this repository. The application does not install/connect the Cloudflare account MCP or deploy itself as a hidden setup step. There is no automatic provider connection or business DNS change.

## Retained module inventory

Every line is part of the approved extraction scope. The destination implementation map must name its actual runtime and UI entry points and tests as Dev completes it. A module is not done merely because a configuration row exists or a route says that the feature is available.

1. **Public website and content:** theme tokens, reusable page rendering, service/offering catalog, business settings, SSR/public routes, and safe published content snapshots.
2. **Owner admin, audit, and credentials:** owner console, allowlisted identity, session lifecycle, credential save/readiness/rotation/revocation, audit readback, and safe admin operations.
3. **Hosted scheduler:** configured hosted-booking link/catalog/context and owner inspection/configuration. It remains optional and distinct from local requests.
4. **Historical API booking:** provider catalog/availability, customer OTP identity, booking create/read/report, cancellation/reschedule, webhook ingestion, reconciliation, payment-eligibility policy, and provider diagnostics where previously implemented. These operations remain isolated and default-off; an inquiry never becomes a provider-confirmed appointment.
5. **Contact and preferred-date requests:** public intake, persisted request lifecycle, owner inbox/status, separate notification outbox/configuration/transport, retention, and delivery readback.
6. **Google customer integration:** customer sign-in/identity, profile and booking-form prefill, preferences and account operations, with customer/admin identity separation.
7. **Google Business/reviews integration:** owner OAuth connection, selected-location configuration, normalized review display and connection lifecycle, independently optional and never fabricated.
8. **Consent, tags, analytics, and measurement:** purpose-specific consent grants, tag/configuration management, analytics collection/reporting and element/document measurement; withdrawal and payload allowlists remain enforced.
9. **Experiments, compiler, and cache:** experiment versions, eligible assignment/exposure, consented feedback, immutable public artifact compilation, validation, cache behavior and safe promotion/rollback.
10. **Visitor assistance:** visitor help/session/thread persistence, grounding, feedback, preference context, exports/forget/retention boundaries, and supported public help operations.
11. **Private photo assistance:** optional photo configuration, normalized private upload/storage, bounded observation, health diagnostics and deletion. No photo bytes or derived content may enter analytics or shared memory.
12. **Admin chat and memory:** owner-protected chat, typed operation registry, persisted human approvals for consequential operations, per-admin private interaction memory, installation-scoped shared curation, deletion/undo, provenance and vector lifecycle.
13. **Analytics, AI and background work:** deterministic local analysis and bounded jobs operate without AI; optional model analysis, provider-backed analytics and scheduled/background processing have explicit readiness, consent, provenance, cost and retry gates.
14. **Optional standalone MCP:** separately authenticated adapter to a strict operation allowlist. It never bypasses browser/admin authorization, exposes arbitrary SQL/shell/URL/secret actions, or becomes required for installation.

This inventory must be reconciled against source modules and the destination implementation/test map. If an operation cannot be carried forward as a working optional feature, report the specific gap to Lead and Architect for a scope decision. Do not silently shrink the approved scope or call a stub retained behavior.

## Implementation and QA sequence

1. **Framework and schema extraction:** preserve the complete Vinext route/component/domain-service graph and original relational model. Replace only Sites-specific build/auth/proxy/scheduling operations. Keep checked-in Drizzle migration ancestry and prove records survive additive migrations.
2. **Standalone identity and provisioning:** install the pinned Cloudflare/Vinext bootstrap helper, Workers bindings and stable install identifier; provision Google owner allowlist before any admin use; establish secure session, CSRF, cookie, return-path and audit boundaries. Prove clean startup without optional provider credentials or AI.
3. **Business/site draft lifecycle:** retain existing public rendering, offerings, content and compiler services. Add the new manual onboarding flow, source-backed deterministic draft from manually entered details or explicitly pasted source text, owner review and revision-bound explicit publish. A provided HTTPS URL is metadata only; source retrieval remains disabled. Reject private/non-HTTPS URL values and assert zero outbound calls. Preserve prior published content on failed/stale publication.
4. **Admin configuration and operations:** retain existing admin UI and module operations; adapt identity/credential/admin routes without reducing them to generic feature CRUD. Each readiness/config setting remains connected to a real module operation.
5. **Provider and customer modules:** preserve hosted scheduling, historical booking/customer OTP, notifications, Google customer/reviews services, consent, analytics, experiments, compiler/cache, visitor help/preferences/feedback/photos and their persistence semantics. Use injected providers in tests and test enabled behavior and zero-call disabled paths.
6. **Admin intelligence and jobs:** preserve typed chat operations, approval receipts, private/shared memory, vector lifecycle, deterministic analytics, AI analysis and background operations. Recheck global/per-feature AI gates on direct and queued dispatch.
7. **Optional MCP:** preserve its typed operations and separately authenticated machine boundary. Configure a default-off owner-bound bearer with typed scopes where machine use is supported; never use a browser-session fallback as machine authentication.
8. **Integration acceptance:** QA adapts and sanitizes relevant original regressions and adds target-native Worker HTTP/D1 tests. Root/Lead coordinates build, deployment, secrets and hosted checks. Compare every inventory line to actual route/page/operation and enabled success-path tests before claiming retention.

## Acceptance and known limits

The detailed checkbox contract is in [`ACCEPTANCE.md`](ACCEPTANCE.md); implementation-to-test traceability is in [`MODULE_TEST_MAP.md`](MODULE_TEST_MAP.md). At minimum, acceptance proves safe optional-dependency absence, explicit owner provisioning, cross-user denial, CSRF/origin enforcement, audit and secret redaction, CAS conflicts, validated import SSRF boundaries, draft approval and published revision continuity, meaningful enabled behavior per module, and zero outbound provider/AI calls when disabled or unconfigured.

Use synthetic isolated local D1 state and injected authentication/provider seams. Tests must not submit real bookings, send messages/OTP, trigger webhooks, charge/payment operations, or consume paid AI. Verify failure paths and resulting database state, not only status codes. The project needs a current official Cloudflare deployment/build path, but a local build does not prove the hosted binding, identity, migration, or version.

No approved browser or hosted Cloudflare acceptance session is available to QA at this stage. Browser UI, actual OAuth, provider account readiness, successful delivery/booking, Cloudflare deployment, D1 binding and persistence, AI provider operation, and live machine-MCP authentication remain **unverified** until an owner/authorized operator deliberately performs and records them. Do not report them as passed based on compilation, mocks, source code, or an expected URL.
